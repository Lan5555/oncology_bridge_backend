# Marketplace deployment

Apply `marketplace.sql` once to PostgreSQL after the existing facility, Oncosourz and GS1 schema migrations. Back up and review the migration before applying it. The application uses `synchronize: false`. This migration is additive and does not guess pack units for existing stock.

Also apply `inventory-access.sql` before starting this version. It adds individual facility-bound stock grants and catalogue ownership. It does not automatically grant stock access to every facility admin, doctor or pharmacist.

## Stock intake and staff authorization

Designate the responsible stock admin and authorized staff with `PUT /api/users/:userId/stock-access`, body `{ "enabled": true }`. This audited endpoint requires a network administrator with `admin.access` and `user.update` (plus the configured MFA policy). It grants only `inventory.manage` for that user's current facility. `{ "enabled": false }` removes that individual grant; a role-level `inventory.manage` grant continues to apply. The response returns effective assigned permissions and `sessionRefreshRequired: true`. Use the existing role permission API when an entire deliberately chosen role should have stock access. Avoid granting it to a general professional role unless every member should receive it.

The designated admin may have account type PHARMACIST or DOCTOR; stock permission does not depend on PHARMACY_STORE. `facility.users.manage` remains separate and does not imply stock access or let facility admins self-assign stock grants. `inventory.manage` does not grant `marketplace.list` or bypass marketplace seller requirements.

After assignment, the affected client must call `POST /auth/api/refresh` with its existing refresh token and replace its stored user and tokens. Login, refresh, and `GET /api/me` merge current role and individual grants into `permissions` and `allowed_pages`. Refreshed JWTs include these navigation claims. Active verified stock members receive `pg-inventory`, `pg-scan`, and `pg-medicines` alongside their other pages. Unverified, inactive, or suspended facility members receive only dashboard/settings and no effective stock grant in their user response. Stock endpoints recheck database grants on each operation, so revocation applies before the next token refresh. Individual grants do not follow users to another facility.

Manual intake, inventory mutations, GS1 decode, scan recording and scan batches require `inventory.manage`; any supplied facility ID must match the authenticated membership. Both intake paths use the same `inventory` table. Existing catalogue granular permissions remain supported for their respective operations. Facility staff can create catalogue entries with server-derived ownership and edit/delete only their facility-owned entries. Existing catalogue entries have NULL ownership and remain shared, readable for intake, and writable only by network administrators with the corresponding `medicine.create`, `medicine.update` or `medicine.delete` permission. GTIN catalogue lookup and inventory intake remain shared across facilities. Once another facility holds inventory referencing a facility-owned record, edits/deletion also require network administration; medicine row locks serialize these changes with new stock references. Review existing records before explicitly assigning ownership; do not bulk-assign shared catalogue records to one facility.

Configure the server using the marketplace settings in `.env.example`. Keep Cloudinary API credentials and the Paystack secret key on the backend. `FRONTEND_ORIGIN` must be an HTTPS origin present in `CORS_ORIGIN`. Paystack callbacks go to `/pay/<invoiceReference>` on that origin. Configure the Paystack webhook as `POST <backend>/api/payments/paystack/webhook`.

Grant `marketplace.list` in `role_permissions` only to seller roles approved to list stock. A seller must also have `account_type=PHARMACY_STORE`, an active facility, an active verified account, and a latest verified application. Buyers must have verified DOCTOR, PHARMACIST or PHARMACY_STORE accounts. Seller verification in listing responses comes from the creator's latest verification record.

Set each batch's reviewed `inventory.selling_unit` to `vial`, `pack`, `bottle` or `box`; inventory creation/update accepts `sellingUnit`. Existing batches remain unlistable until this is supplied. Set product-specific approved `medicines.storage_temperature` text; listing storage must match it after trimming. `medicines.prescription_required` defaults to true for every medicine. An authorized catalogue administrator must review the classification before setting it false; seller submissions cannot relax it. This field is intentionally not writable through the seller listing form.

The current contract charges the medicine subtotal with no additional platform fees (`fees_kobo=0`). Add any future fee policy before order creation and include it in the immutable total. Prices and calculations use integer kobo, exposed as numeric NGN.

Marketplace invoices are persisted as part of `marketplace_orders`, with their own unique invoice reference, line/seller snapshots and payment data. `GET /api/invoices/:reference` reads these through the existing invoice route and requires the buyer's bearer token. Its existing fields are preserved and `paystackUrl`, `expiresAt`, and `fulfillmentState` are supplied. Legacy invoices retain their existing access behavior. No patient details are returned by marketplace invoice reads.

Stock remains in `inventory.quantity`. Reservations subtract from visible availability without decrementing inventory. A database trigger protects reserved quantities and listed batch identity from legacy writes; inventory edits and transfer decisions now lock their rows, and scans increment atomically. One listing is allowed per batch. Batches with inactive sellers, deleted medicines, non-AVAILABLE state or expiry today or earlier cannot be bought. Catalogue filters and pagination run in SQL with stable ID tie-breakers.

The in-process maintenance worker runs every 30 seconds, releases expired reservations, reconciles up to 20 pending/released transactions per pass, and retries orphan-image cleanup. It requires at least one running API instance. Database transactions serialize reservation/payment updates across replicas. Successful payments after release/expiry, or after eligibility changes, enter `PAID_REVIEW` / `PAYMENT_REVIEW_REQUIRED` without decrementing stock. Operations must inspect these records and arrange refund or resolution; there is no automatic refund or clinical dispensing. Paid orders remain `AWAITING_CLINICAL_RELEASE` for existing fulfillment processes. Do not treat payment as delivery.

Cloudinary receives decoded and re-encoded WebP files only, with metadata removed, unique public IDs and ordered stable image IDs. Only JPEG, PNG and WebP inputs are accepted, 1–5 photos, at most 5 MiB per input and 25 million decoded pixels, without animation. Pending upload records are written before contacting Cloudinary. Failed submissions attempt immediate deletion; pending records remain for hourly cleanup retries to also catch delayed uploads after timeouts. Attached images are excluded from cleanup.

Checkout idempotency is scoped to buyer and canonical payload. Initialization retries always use the same persisted Paystack reference. A timeout never generates a replacement reference or fake link. If Paystack accepted initialization but its URL response was lost, it may reject duplicate initialization; reconciliation still detects payment, and the buyer can start a new checkout after the reservation expires. Orders are reconciled even after release so late payments can be flagged.

Run `npm test -- --runInBand` and `npm run build`. Database tests execute the actual migration, queries and triggers against embedded PostgreSQL (PGlite). PGlite serializes transactions through one connection; run a staging check against multi-connection PostgreSQL for concurrent different keys, inventory updates, callbacks and webhook delivery. Tests mock Cloudinary and Paystack; finish acceptance with real image uploads and Paystack test payments using configured test credentials.
