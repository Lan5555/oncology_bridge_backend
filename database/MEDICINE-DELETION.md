# Catalogue medicine deletion

Apply database/medicine-deletion.sql after the existing marketplace and transfer tables/migrations, before deploying this backend. The migration adds transactional guards against scanner/alternate stock writes and transfers racing catalogue deletion. Application-only deployment does not provide these database guards.

DELETE /api/medicines/:id retains the existing server authorization: verified facility members require medicine.delete or inventory.manage, own the catalogue row, and cannot change a medicine stocked by another facility; those shared records require authorized network administration (admin.access and medicine.delete, plus configured admin MFA).

Deletion runs atomically with the audit entry. It soft-deletes the medicine, suspends linked listings, releases outstanding marketplace reservations, and flags paid orders awaiting clinical release for payment review. It uses the same advisory lock as marketplace checkout/payment before locking the medicine. Audit description records actor, medicine, affected batch/facility IDs, suspended listing IDs, released reservation IDs and paid-order IDs requiring review. Audit/persistence failure rolls back the whole deletion.

Inventory quantities/statuses and scan, order, invoice, transaction and transfer rows are retained. Physical stock is not disposed. Completed payments and consumed reservation states remain recorded; no stock is credited back and no refund is initiated automatically. Unfulfilled paid orders require staff review. Unpaid orders retain their payment reference/status so reconciliation continues: a late successful payment becomes PAID_REVIEW with RELEASED reservation and no stock decrement. Existing payment links/reservations cannot be used to create a new checkout after deletion. Pending transfers remain in history; approval/new transfer is blocked, while explicit rejection/cancellation is allowed.

Default inventory/expiry queries, pagination totals, stock search, near-expiry lists, inventory statistics, dashboard stock totals/charts/public totals and inventory exports exclude linked deleted medicines. Buyer catalogue, new listings and checkout eligibility also exclude them. Intake cannot select deleted medicines. The database guard rejects new inventory, inventory quantity increases and transfer activity for deleted/missing medicines, including old/scanner write paths.

Authorized historical inventory remains available via GET /api/inventory?includeDeletedMedicines=true with the same membership/facility/read-permission checks and pagination. This flag adds deleted medicine batches to the list; it never changes active stock statistics. GET /api/inventory/:id also preserves the linked soft-deleted medicine. Responses include medicine.active, medicine.deleted_at, medicine_deleted and medicine_active. Historical operational scans, transfers and marketplace records include medicine deletion metadata too. Older unlinked records remain explicitly unlinked; no names are guessed.

Verification uses PostgreSQL-backed tests for deletion, reservation release, suspended buyer options, persisted historical flags, fresh-session inventory reads/totals, late payments, transfer/scanner guards, and rollback when auditing fails. No deployed browser session or production database has been changed by these tests.
