# Admin metrics and prescription review

Apply `prescription-review.sql` after `frontend-contract.sql` and `facility-registration.sql` before deploying the updated Prescription entity or review routes. It adds prescription revisions, optional review fields on existing prescription events, an append-only history guard and a unique event per reviewed revision. It does not approve historical prescriptions or manufacture past decisions. Existing `Cleared` approvals remain stored as-is and are presented as `Approved` by the new admin endpoints; marketplace prescription eligibility accepts both values.

Grant `admin.access` and `prescription.read` to approved network readers; add `prescription.review` only for authorized reviewers. No grants are automatic. Network roles use the existing network-wide scope and MFA checks. A facility administrator with those keys still cannot use the network review routes. Both read and review permission are required to decide, and permissions are rechecked in the write transaction after locking the prescription.

For prescription descriptions, also apply `prescription-description.sql` after the review migration and before deploying description support. Creation and pending-record edits accept optional `description` text up to 2000 characters. Whitespace is trimmed; omitted, null or blank descriptions are stored as null. Creation, operational lists, admin review lists and review details return `description`. Edits increment the prescription revision, invalidating stale review drafts; authorization preserves the description. Descriptions stay with the clinical record and are not sent by email. Add a multiline Description input to the frontend create/edit form and display the saved value in review details.

## Dashboard counts

Authenticated `GET /api/dashboard/summary` preserves existing fields and scope enforcement and adds `activeUsers` and `totalInventoryItems`. The same repeatable-read snapshot supplies timestamps, counts and existing stock metrics. `activeUsers` counts enabled accounts in scope, excluding physically absent records and any recorded soft-delete timestamp. It counts accounts, not visitors or concurrent sessions; network counts include active administrator accounts. `totalInventoryItems` counts inventory records/batches, regardless of quantity or selling unit, excluding soft-deleted records and records linked to a deleted medicine. Facility requests count only their authenticated facility. Where the deployed users/inventory schema lacks a soft-delete field, no synthetic deletion status is invented.

The current available-stock and 60-day near-expiry calculation is preserved, with missing status/quantity/expiry data kept unavailable rather than treated as zero. Aggregate query errors remain failures. `valueRecoveredNaira` remains null: there is no agreed completed-redistribution valuation, currency/conversion, duplicate or reversal policy. Marketplace checkout revenue is not recovery value.

## Review API

All routes require a bearer access token and return `{success,message,data}`. Responses use only saved pseudonymous patient references, clinical prescription fields and display metadata; no patient name/contact lookup, credential, provider body or email payload is included. GET and decision responses set private/no-store cache headers.

| Method | Route | Data |
| --- | --- | --- |
| GET | `/admin/api/prescriptions?page=1&limit=20&authStatus=Pending&q=...` | `{items,pagination:{page,limit,total,totalPages}}` |
| GET | `/admin/api/prescriptions/:id` | Saved review record plus `version`, `allowedDecisions`, chronological `events` |
| POST | `/admin/api/prescriptions/:id/decision` | Complete updated detail (HTTP 200) |

Filters combine with AND after authorization. `authStatus` is exactly `Pending`, `Approved` or `Rejected`; omit it for all. Search matches patient reference, medicine generic/brand name, pharmacy or prescriber display name. Default page is 1, default limit 20, maximum 100. Invalid/unknown filters fail; empty results have total/totalPages 0. Sort is created_at descending, then ID descending. Legacy cleared records participate in the Approved filter.

The review list contains `id`, `patient_ref`, `icd10`, `tnm_stage`, `insurer`, `qty`, `auth_status`, `order_stage`, `pharmacy`, `pharmacy_name`, `medicine`, `prescriber`, and `created_at`. Pharmacy contains id/name/city/state/status, medicine contains id/name/strength, and prescriber contains id/name. Missing related records are null; an absent historical insurer is an empty string, not an invented insurer or coverage status. Detail events expose id/type/message/createdAt/actorName. Creation events reuse actual saved creation history; decision events store the reviewer's reason and actor identity.

Submit `{decision:"APPROVE"|"REJECT",expectedVersion:1,reason:"Recorded decision reason"}`. The reason is trimmed and must be 1–1000 characters. Client identities, timestamps, authorization/payment states and any other extra write fields are rejected. Read-only admins always receive no allowed decisions. Pending/Waiting records can offer APPROVE/REJECT only when current prescriber, medicine, selected pharmacy and positive quantity/saved insurer are eligible. The prescriber must be an enabled verified doctor in an active nondeleted facility, with a verified latest licence application if one exists. The medicine must remain current and accessible in the prescriber's catalogue. The selected active nondeleted pharmacy must have an enabled verified pharmacist/store account. Suspended/deleted/dispensed/cancelled/reviewed/ineligible records cannot be decided.

This is an internal platform authorization decision; it does not assert external insurer coverage. This workflow does not currently require external insurer confirmation as an eligibility condition. A future policy requiring coverage confirmation must add persisted authoritative evidence and a backend eligibility check before offering APPROVE. No insurer API call, payment, checkout, marketplace order, stock deduction or clinical email is triggered by review.

The decision transaction locks the prescription, rechecks permissions and revision, holds linked account/facility/medicine eligibility rows, and rechecks current eligibility. It updates only auth_status to Approved/Rejected, increments revision, appends a prescription event and audit event, and preserves clinical fields, patient reference, selected pharmacy, insurer and order_stage. A stale or repeated decision returns 409 with no new event or side effect. Failures roll back status, revision and history together. Unknown/missing records return 404; missing authentication 401; insufficient permissions/MFA 403; invalid input 400/422.

Generic `PATCH /api/prescriptions/:id` can edit only clinical/input fields on Pending/Waiting records within the caller's facility or their own prescribing scope. It rejects authorization, stage, ownership, identity, timestamps, display ID and revision writes, even from an admin. Clinical changes increment the revision so an open review draft must be reloaded. Finalized records cannot be rewritten using that route. Authorization decisions must use the protected review endpoint. There is no new dispensing-stage transition endpoint in this change.

## Verification

The HTTP/PostgreSQL tests cover scope and explicit permissions, MFA, saved-record display, filtering/pagination, canonical legacy approvals, simultaneous reviewers, stale drafts after clinical edits, ineligible dependencies, request validation, atomic rollback on audit failure and generic PATCH bypass prevention. Dashboard tests cover scoped counts, disabled/deleted users, genuine zeros, deleted medicines, batch versus quantity semantics, missing-stock data and aggregate errors. Provider operations are not invoked. PGlite serializes database connections; separate-connection PostgreSQL contention still needs deployment verification. No environment files are loaded by these tests.
